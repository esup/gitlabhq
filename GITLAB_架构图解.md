## 请求处理流程

### HTTP/HTTPS 请求流程

```
┌────────────┐
│  用户请求   │
│ (浏览器)    │
└─────┬──────┘
      │ 1. HTTPS 请求 (端口 443)
      ▼
┌────────────┐
│   NGINX    │
│  (反向代理) │
└─────┬──────┘
      │ 2. 转发到 Workhorse (Unix Socket)
      ▼
┌────────────────────┐
│ GitLab Workhorse   │
│  (智能代理)        │
└─────┬──────────────┘
      │
      │ 3. 判断请求类型
      ├────────────────┬────────────────┬─────────────────┐
      │                │                │                 │
      ▼                ▼                ▼                 ▼
  静态文件        Git HTTP        文件上传           API/Web
   (直接返回)      请求            (直接处理)          请求
      │                │                                 │
      │                ▼                                 │
      │         ┌──────────┐                            │
      │         │  Gitaly  │                            │
      │         │(Git操作) │                            │
      │         └──────────┘                            │
      │                                                  │
      └──────────────────────────────────────────────────┘
                              │
                              ▼
                      ┌──────────────┐
                      │  Puma (Rails)│
                      │   应用服务器  │
                      └──────┬───────┘
                             │
                ┌────────────┼────────────┐
                │            │            │
                ▼            ▼            ▼
          ┌──────────┐ ┌────────┐ ┌──────────┐
          │PostgreSQL│ │ Redis  │ │  Gitaly  │
          │ (数据库) │ │(缓存)  │ │(Git RPC) │

```

## CI/CD 流水线流程

```
┌─────────────────┐
│  开发者推送代码  │
│  git push       │
└────────┬────────┘
         │ 1. 触发 Webhook
         ▼
┌─────────────────┐
│   Sidekiq       │
│ (后台任务队列)  │
└────────┬────────┘
         │ 2. 创建 Pipeline
         ▼
┌──────────────────────────────────────┐
│            Pipeline                   │
│                                       │
│  ┌──────────┐  ┌──────────┐  ┌────┐ │
│  │ Stage 1  │→ │ Stage 2  │→ │... │ │
│  │  (构建)  │  │  (测试)  │  │    │ │
│  └──────────┘  └──────────┘  └────┘ │
└──────────────────────────────────────┘
         │
         │ 3. 每个 Stage 包含多个 Jobs
         ▼
┌──────────────────────────────────────┐
│         Stage: Build (构建)          │
│                                       │
│  ┌─────────┐  ┌─────────┐  ┌──────┐ │
│  │ Job 1   │  │ Job 2   │  │Job 3 │ │
│  │compile  │  │package  │  │lint  │ │
│  └─────────┘  └─────────┘  └──────┘ │
└──────────────────────────────────────┘
         │
         │ 4. GitLab Runner 拉取并执行 Job
         ▼
┌─────────────────┐
│ GitLab Runner   │
│  ┌───────────┐  │
│  │ Executor  │  │
│  │ (Docker/  │  │
│  │  Shell/   │  │
│  │  K8s)     │  │
│  └───────────┘  │
└────────┬────────┘
         │ 5. 执行脚本，上传结果
         ▼
┌─────────────────┐
│  Object Storage │
│  (Artifacts)    │
└─────────────────┘
         │
         │ 6. 更新 Pipeline 状态
         ▼
┌─────────────────┐
│  PostgreSQL     │
│  (状态存储)     │
└─────────────────┘
```

## 总结

通过这些图表，我们可以清晰地看到：

1. **GitLab 的分层架构**：从客户端到存储层，每一层都有明确的职责
2. **请求处理流程**：Workhorse 作为智能代理，优化了请求处理
3. **数据存储策略**：使用不同的存储系统存储不同类型的数据
4. **异步任务处理**：通过 Sidekiq 实现高效的后台任务处理
5. **性能优化**：多层缓存策略确保系统性能

这些设计使得 GitLab 能够：
- ✅ 处理大规模并发请求
- ✅ 支持复杂的业务逻辑
- ✅ 保持良好的代码可维护性
- ✅ 实现水平扩展
- ✅ 提供优秀的用户体验
